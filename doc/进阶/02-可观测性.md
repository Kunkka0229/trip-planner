# P2：可观测性：日志、Trace 与成本

> **需求卡片**
> 线上用户反馈："生成的行程第三天是空的。"你在本地试了十几次都复现不出来。老板还顺带问了两个问题："现在一次规划平均花多少钱？""最慢的那些请求慢在哪？"
> 本迭代：**每一次规划请求都要能事后完整回放**，包括每一步的输入输出、耗时、token 和成本，并且能按用户查找。

**目标**：搭起 Agent 系统的"眼睛"。学完你会掌握：结构化日志 + request_id 贯穿全链路、自部署 Langfuse、用 CallbackHandler 零侵入地追踪 LangGraph、给 trace 打上用户和标签、收集用户反馈。

> 本课代码用一个**假的 Langfuse 服务器**接收上报数据验证过：trace 里有 `trip_plan → trip_graph → collect / attractions / generate / validate` 全部节点和 `user_id`；trace_id 确实由 request_id 算出；反馈分数通过 `/api/public/ingestion` 发出；后台线程和 LangGraph 并行节点里的日志都带着正确的 request_id。**没有在真实的 Langfuse 上验证界面效果**，下面的界面描述来自官方文档。

## 为什么 Agent 系统特别需要可观测性

普通后端接口出了问题，看报错堆栈基本就能定位。Agent 系统不一样：

1. **不报错的错误**。模型返回了一份"格式正确但内容离谱"的行程，没有任何异常，日志里一片祥和。
2. **不确定性**。同样的输入，这次好、下次坏。你复现不出来，只能看"当时"到底发生了什么。
3. **链路长**。一次请求里有 4 次高德调用、1~3 次大模型调用、校验、grounding，问题可能出在任何一步。
4. **花钱**。每次调用都有 token 成本，不统计就不知道钱花在了哪。

所以 Agent 的可观测性要回答的问题是：**这一次请求，每一步看到了什么、输出了什么、花了多久、花了多少钱**。这就是 trace（链路追踪）。

| 工具 | 回答什么问题 | 本课 |
|---|---|---|
| 日志（logging） | 发生了什么事件、有没有报错 | `print` → `logging`，每行带 request_id |
| Trace（Langfuse） | 一次请求的完整过程和每一步的输入输出 | 自部署 Langfuse，CallbackHandler 接入 |
| 指标（Metrics） | 整体趋势：成功率、P95 延迟、日均成本 | Langfuse 的 Dashboard 自带 |
| 反馈（Scores） | 用户觉得好不好 | 👍 / 👎 写回 trace |

## 为什么选 Langfuse

| | Langfuse | LangSmith |
|---|---|---|
| 出品方 | 开源社区（MIT 协议） | LangChain 官方 |
| 部署 | 可以自部署，数据不出公司 | 主要是 SaaS，自部署要企业版 |
| 和 LangChain 的集成 | 一个 CallbackHandler | 设两个环境变量，零代码 |
| 适合 | 国内公司（数据合规）、多框架混用 | 全家桶都是 LangChain 的团队 |

两者的概念几乎一样，学会一个，另一个半小时就能上手，主要是换个名词：

| 概念 | Langfuse | LangSmith |
|---|---|---|
| 一次完整请求 | Trace | Trace |
| 其中的每一步 | Observation（Span / Generation） | Run（嵌套成树） |
| 多轮对话串起来 | Session | Thread |
| 打分 | Score | Feedback |

本课选能自部署的 Langfuse：数据全在自己电脑上、不用注册外部服务、开源免费不限量。国内公司对"用户数据不能出境"很敏感，这也是公司里常见的选择。

## Step 0：部署 Langfuse

Langfuse 自部署需要 Postgres、ClickHouse、Redis、MinIO 等好几个服务，一个个手动装太麻烦。官方写好了一份 `docker-compose.yml`，用 Docker 一条命令就能全部启动。这一步分四小步：装 Docker → 启动 Langfuse → 建账号拿 Key → 学会日常启停。

### 0.1 安装 Docker Desktop

先花一分钟理解三个概念（前端类比）：

| 概念 | 是什么 | 前端类比 |
|---|---|---|
| 镜像（image） | 打包好的"软件 + 运行环境"，只读 | 发布到 npm 上的包 |
| 容器（container） | 镜像运行起来的实例，可以启动、停止、删除 | `npm run dev` 跑起来的那个进程 |
| Compose | 用一个 yml 文件描述多个容器怎么一起启动 | `package.json` 里一条脚本同时拉起前端、后端、mock 服务 |

你的 Mac 是 Apple 芯片（arm64），用 Homebrew 安装最省事：

```bash
brew install --cask docker-desktop
```

> 不用 Homebrew 的话，去 https://www.docker.com/products/docker-desktop/ 下载 **Mac with Apple chip** 版本的 dmg，拖进"应用程序"。

装好后**第一次要手动打开**：在"应用程序"里打开 Docker（或者终端执行 `open -a Docker`），同意许可协议。提示登录时可以直接跳过（Skip），本地使用**不需要注册 Docker 账号**。等菜单栏的鲸鱼图标不再闪动，就说明启动好了。

验证一下：

```bash
docker --version           # 能输出版本号，说明命令行装好了
docker compose version     # Compose v2，Docker Desktop 自带
docker run --rm hello-world   # 拉一个测试镜像跑一下，看到 "Hello from Docker!" 说明一切正常
```

**资源设置**：Docker Desktop → Settings → Resources，内存（Memory）至少给 **6 GB**（Langfuse 加上 ClickHouse 比较吃内存，默认值一般够用，不够时容器会反复重启）。

> **国内网络拉镜像慢或超时**：Langfuse 的镜像来自三个地方：`docker.langfuse.com`、Docker Hub（`docker.io`）、`cgr.dev`。最稳的办法是让 Docker 走代理：Settings → Resources → Proxies，填上你的代理地址。只配 Docker Hub 镜像加速器（Settings → Docker Engine 里的 `registry-mirrors`）**只对 `docker.io` 的镜像有效**，另外两个地方的镜像还是会慢。国内公开的加速地址经常变动失效，拉不下来时把报错发给我。

### 0.2 启动 Langfuse

只需要官方的 `docker-compose.yml` 这一个文件，不用克隆整个仓库：

```bash
mkdir -p ~/langfuse && cd ~/langfuse
curl -fsSL -o docker-compose.yml https://raw.githubusercontent.com/langfuse/langfuse/main/docker-compose.yml
# 下载不了的话，也可以克隆仓库：git clone --depth 1 https://github.com/langfuse/langfuse.git ~/langfuse

docker compose up -d     # -d：后台运行。第一次要拉好几个镜像（加起来 2~3 GB），比较慢
docker compose ps        # 查看状态，等所有服务都是 running（带健康检查的会显示 healthy）
docker compose logs -f langfuse-web   # 看网页服务的日志，出现 Ready 之类的字样就可以访问了，Ctrl+C 退出日志（服务不会停）
```

启动的 6 个服务：

| 服务 | 作用 | 占用的端口 |
|---|---|---|
| langfuse-web | 网页界面 + 接收 SDK 上报的 API | **3000** |
| langfuse-worker | 后台处理上报的数据 | 3030 |
| postgres | 存账号、项目、配置 | **5432** |
| clickhouse | 存 trace（分析型数据库，查大量数据很快） | 8123、9000 |
| redis | 队列和缓存 | **6379** |
| minio | 存原始事件和大文件（兼容 S3 的对象存储） | 9090、9091 |

> **注意端口冲突**：Langfuse 占用了 5432（Postgres）和 6379（Redis）。P5 你自己的 Postgres、P12 的 Redis 要换别的端口（比如 5433、6380），**不要连到 Langfuse 的数据库上**。
>
> **关于 `# CHANGEME`**：compose 文件里的密码都是默认值（比如 `postgres`、`miniosecret`），文件开头也提醒了要改。只在自己电脑上学习可以不改，大部分端口只绑定在 `127.0.0.1`（本机才能访问）；**部署到服务器上之前一定要全部改掉**。

## Step 2：日志 `app/observability/logs.py`

```bash
mkdir -p app/observability && touch app/observability/__init__.py
```

> 文件名为什么不叫 `logging.py`？因为会和标准库的 `logging` 重名，`import logging` 时可能导入到你自己的文件，引发莫名其妙的错误。**永远不要用标准库的模块名给自己的文件命名**（`json.py`、`queue.py`、`typing.py` 同理）。

```python
"""日志：每一行都带上 request_id，一次请求的所有日志可以用它串起来

为什么不用 print？
  - print 没有级别：线上想只看 WARNING 以上的，做不到
  - print 没有上下文：10 个用户同时请求，日志交错在一起，分不清哪行是谁的
  - print 不能统一格式：日志平台（ELK、Loki、阿里云 SLS）需要固定格式才能检索
"""

import logging
from contextvars import ContextVar

# ContextVar：每个请求（准确说是每个"执行上下文"）各自独立的变量
# 两个请求同时在跑，各自 set 自己的值，互不覆盖。前端没有完全对应的东西，
# 最接近的是 Node 的 AsyncLocalStorage：在异步调用链里隐式传递的"请求级全局变量"
request_id_var: ContextVar[str] = ContextVar("request_id", default="-")


class RequestIdFilter(logging.Filter):
    """日志过滤器：每条日志输出前，把当前的 request_id 塞进 record，格式字符串里就能用 %(request_id)s"""

    def filter(self, record: logging.LogRecord) -> bool:
        record.request_id = request_id_var.get()
        return True  # 返回 True 表示这条日志照常输出


def setup_logging(level: str = "INFO") -> None:
    handler = logging.StreamHandler()  # 输出到终端（stderr）
    handler.addFilter(RequestIdFilter())
    handler.setFormatter(
        logging.Formatter("%(asctime)s %(levelname)-7s [%(request_id)s] %(name)s: %(message)s", datefmt="%H:%M:%S")
    )
    root = logging.getLogger()  # 根 logger：所有 logging.getLogger(__name__) 创建的 logger 最终都会交给它输出
    root.handlers = [handler]  # 覆盖掉默认的 handler，避免重复输出
    root.setLevel(level.upper())
    # 第三方库的日志太吵，只看警告以上
    for noisy in ("httpx", "httpcore", "openai", "urllib3"):
        logging.getLogger(noisy).setLevel(logging.WARNING)
```

**ContextVar 是本课最重要的概念**。request_id 要出现在"这次请求的每一行日志"里，但日志可能在路由、图节点、高德客户端里的任何地方打印，总不能把 request_id 当参数一层层传下去。ContextVar 就是"隐式传递的请求级变量"：中间件 `set` 一次，这次请求的调用链里任何地方都能 `get` 到，而且不同请求之间互不干扰。

## Step 3：把 print 换成 logger

`app/graph/collect.py` 和 `app/graph/trip_graph.py` 顶部加上：

```python
import logging

logger = logging.getLogger(__name__)   # __name__ 是模块名，例如 app.graph.collect，日志里会显示出来
```

然后把节点里的 `print` 换掉：

```python
# collect.py
logger.warning("工具 %s 失败: %s", name, exc)

# trip_graph.py
logger.warning("第 %d/%d 次调用失败: %s", attempt, MAX_ATTEMPTS, error_reason(exc))       # generate
logger.warning("第 %d/%d 次校验失败: %s", state["attempts"], MAX_ATTEMPTS, error_reason(exc))  # validate
logger.info("Grounding: 景点命中率 %.0f%%，未匹配 %s", stats["attraction_rate"] * 100, stats["ungrounded"])
logger.error("大模型多次生成失败，返回兜底方案")                                         # fallback
```

> **为什么写 `logger.warning("工具 %s 失败", name)`，而不是 f-string `logger.warning(f"工具 {name} 失败")`？**
> 用 `%s` 占位时，只有这条日志真的要输出才会去拼接字符串；级别不够被过滤掉时，拼接的开销就省了。更重要的是，日志平台可以按"模板"聚合：`工具 %s 失败` 出现了 500 次，比 500 条各不相同的字符串好分析得多。`%.0f%%` 里的 `%%` 是输出一个百分号。

其他文件里的 `print` 可以留着，作业 1 让你自己全部换掉。

## Step 4：Trace `app/observability/tracing.py`

```python
"""Langfuse 链路追踪：一次规划请求 = 一条 trace，里面每个图节点、每次大模型调用都是一个 span

trace（链路）
└── trip_plan                     ← 我们手动创建的根 span，带 user_id、tags、输入输出
    └── trip_graph                ← LangGraph 整张图（CallbackHandler 自动创建）
        ├── collect
        │   ├── attractions / hotels / foods / weather
        │   └── assemble
        ├── generate
        │   └── ChatOpenAI        ← generation：prompt、回复、token 数、耗时、成本
        └── validate

没配置 Langfuse 的 Key 时，所有函数都退化成"什么都不做"，不影响业务（和第 6 课没配 LLM 时退回 mock 是一个思路）
"""

import logging
from collections.abc import Generator
from contextlib import contextmanager
from functools import lru_cache
from typing import Any

from langchain_core.callbacks import BaseCallbackHandler
from langfuse import Langfuse, propagate_attributes
from langfuse.langchain import CallbackHandler

from app.config import get_settings
from app.observability.logs import request_id_var

logger = logging.getLogger(__name__)


@lru_cache
def get_langfuse() -> Langfuse | None:
    settings = get_settings()
    if not (settings.langfuse_public_key and settings.langfuse_secret_key):
        return None
    logger.info("Langfuse 已启用: %s", settings.langfuse_base_url)
    # Langfuse 客户端在后台线程里攒一批数据再上报（批量 + 异步），不会拖慢请求
    return Langfuse(
        public_key=settings.langfuse_public_key,
        secret_key=settings.langfuse_secret_key,
        base_url=settings.langfuse_base_url,
        environment=settings.app_env,  # dev / prod 的数据分开看
        release=settings.app_version,  # 按版本对比效果：新版本上线后成功率是升了还是降了
    )


def langchain_callbacks() -> list[BaseCallbackHandler]:
    """传给 LangChain / LangGraph 的回调。CallbackHandler 会把图的每一步、每次模型调用都上报"""
    langfuse = get_langfuse()
    if langfuse is None:
        return []
    # public_key 用来找到上面创建的那个客户端（同一个进程里可以有多个 Langfuse 项目）
    return [CallbackHandler(public_key=get_settings().langfuse_public_key)]


@contextmanager
def trace_span(name: str, *, user_id: str | None = None, session_id: str | None = None,
               tags: list[str] | None = None, input: Any = None) -> Generator[Any, None, None]:
    """创建根 span，并把 user_id / session_id / tags 传播给它下面的所有 span

    用法：
        with trace_span("trip_plan", user_id="u1", input=...) as span:
            ...                          # 这里面的大模型调用都会挂到这条 trace 下
            if span: span.update(output=...)
    """
    langfuse = get_langfuse()
    if langfuse is None:
        yield None
        return

    # 用 request_id 当种子生成 trace_id：同一个 request_id 永远得到同一个 trace_id
    # 好处：日志里看到 request_id，就能直接算出 trace 的地址，反过来也一样
    request_id = request_id_var.get()
    trace_id = Langfuse.create_trace_id(seed=request_id) if request_id != "-" else Langfuse.create_trace_id()

    # with A as a, B：同时进入两个上下文管理器，相当于嵌套两层 with
    with (
        langfuse.start_as_current_observation(
            name=name, as_type="agent", input=input, trace_context={"trace_id": trace_id}
        ) as span,
        # propagate_attributes：在这个 with 块里创建的所有 span 都自动带上这些属性
        # 这样在 Langfuse 里按用户筛选时，能筛出完整的链路，而不只是根 span
        propagate_attributes(user_id=user_id, session_id=session_id, tags=tags, trace_name=name),
    ):
        yield span


def score_trace(trace_id: str, name: str, value: float, comment: str = "", data_type: str = "NUMERIC") -> bool:
    """给一条 trace 打分（用户反馈、自动评测结果都用它），返回是否成功提交"""
    langfuse = get_langfuse()
    if langfuse is None:
        return False
    langfuse.create_score(trace_id=trace_id, name=name, value=value, comment=comment or None, data_type=data_type)
    return True


def shutdown_tracing() -> None:
    """服务关闭前调用：把还没上报的数据全部发出去，否则最后几条 trace 会丢"""
    langfuse = get_langfuse()
    if langfuse is not None:
        langfuse.shutdown()
```

**要点**

1. **两层 span**。`CallbackHandler` 能自动记录图里的一切，为什么还要手动包一层 `trace_span`？因为图不知道"这是哪个用户的请求""用的是哪种规划模式"，这些是业务信息，要在外层加上。另外 `propagate_attributes` 会把 `user_id` 传给里面的**每一个** span，在 Langfuse 里按用户筛选时，看到的是完整链路。
2. **trace_id 由 request_id 算出来**。`create_trace_id(seed=...)` 是确定性的：同样的种子，永远得到同样的 trace_id。用户报错时把响应头里的 `X-Request-ID` 发给你，你在日志里搜它，再算出 trace_id，打开 `http://localhost:3000/project/<项目ID>/traces/<trace_id>`，就能看到当时的全部细节。
3. **"没配置就什么都不做"**。所有函数在 `get_langfuse()` 返回 `None` 时都直接跳过。本地开发不需要 Langfuse。这是接入任何"旁路"系统（监控、埋点、日志平台）的基本原则：**旁路系统挂了，主业务不能受影响**。
4. **shutdown**。Langfuse 在后台线程里攒一批再发（默认几秒一次）。进程退出时如果不 `shutdown()`，最后几秒的数据就丢了。

# ---------- request_id 中间件（P2）----------
# 每个请求分配一个 ID：优先用调用方传来的 X-Request-ID（网关、前端都可能传），没有就生成一个
# 这个 ID 会出现在：本次请求的每一行日志、响应头、Langfuse 的 trace_id（由它算出来）
# 用户报错时只要把响应头里的 X-Request-ID 发给你，就能找到这次请求的全部信息
@app.middleware("http")
async def add_request_id(request: Request, call_next):
    request_id = request.headers.get("X-Request-ID") or uuid.uuid4().hex
    token = request_id_var.set(request_id)  # set 返回一个 token，用来在结束时恢复原值
    try:
        response = await call_next(request)  # 交给后面的中间件和路由处理，相当于 Express 的 next()
    finally:
        request_id_var.reset(token)
    response.headers["X-Request-ID"] = request_id
    return response
```

# ---------- 第 11 课：SSE 流式接口，推送真实进度 ----------
# SSE（Server-Sent Events）：服务端通过一个一直不关闭的 HTTP 响应持续推送消息，格式是
#   data: {...JSON...}\n\n
# 比 WebSocket 简单：单向推送（服务端 → 浏览器）、基于普通 HTTP、经过代理也没问题
@router.post("/plan/stream", summary="生成旅行计划（SSE 推送进度）")
def plan_trip_stream(
    request: TripRequest,
    planner: Planner | None = Depends(get_trip_planner),
    user_id: UserId = "anonymous",
):
    # 线程安全的队列：后台线程往里放事件，响应生成器从里面取出来发给浏览器
    # 相当于一个"管道"，两头各在一个线程里
    events: queue.Queue[dict | None] = queue.Queue()

    def report(stage: str, percent: int) -> None:
        events.put({"type": "progress", "stage": stage, "percent": percent})

    def worker() -> None:
        try:
            response = run_planner(request, planner, user_id, on_progress=report)
            # mode="json"：保证所有字段都能被 json.dumps 序列化
            events.put({"type": "result", "data": response.model_dump(mode="json")})
        except Exception as exc:  # 高德 Key 错误等异常，也要通知前端，否则前端会一直等下去
            events.put({"type": "error", "message": str(exc)})
        finally:
            events.put(None)  # None 表示"结束了"

    # P2：新线程不会继承当前线程的 ContextVar（request_id 会变成默认值 "-"）
    # copy_context() 拍下当前上下文的"快照"，ctx.run(worker) 在这个快照里执行 worker
    # 这样后台线程里的日志、trace_id 都和这次请求对得上
    ctx = contextvars.copy_context()
    # daemon=True：服务关闭时不用等这个线程结束
    threading.Thread(target=ctx.run, args=(worker,), daemon=True).start()

    def stream() -> Iterator[str]:
        # 海象运算符 :=（Python 3.8+）：赋值的同时判断，相当于
        # while (true) { const event = events.get(); if (event === null) break; ... }
        while (event := events.get()) is not None:
            yield f"data: {json.dumps(event, ensure_ascii=False)}\n\n"

    return StreamingResponse(
        stream(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",  # 不要缓存
            "X-Accel-Buffering": "no",  # 部署在 Nginx 后面时，告诉 Nginx 不要缓冲，否则进度会攒到最后一起发
        },
    )


# ---------- P2：用户反馈 ----------
@router.post("/feedback", summary="对生成的行程打分（👍 / 👎）")
def submit_feedback(body: FeedbackRequest):
    # BOOLEAN 类型的分数：1 = 有帮助，0 = 没帮助。在 Langfuse 里可以统计"好评率"随版本的变化
    ok = score_trace(body.trace_id, "user_feedback", 1 if body.helpful else 0, body.comment, data_type="BOOLEAN")
    return {"success": ok, "message": "感谢反馈" if ok else "未启用 Langfuse，反馈未记录"}
```

**要点**

1. **`ctx.run`：后台线程里 ContextVar 会"丢失"**。第 11 课的 SSE 接口自己开了一个线程，新线程从一个空白的上下文开始，request_id 会变回默认值 `"-"`，trace 也会和这次请求断开。`contextvars.copy_context()` 拍一张当前上下文的快照，`ctx.run(worker)` 在快照里执行 `worker`。
    > 那为什么 FastAPI 的普通 `def` 路由、LangGraph 的并行节点没有这个问题？因为它们内部用线程池执行时，已经帮你做了 `copy_context()`。**只有你自己 `threading.Thread(...)` 的时候才要手动复制**。
2. **`level="WARNING"`**：兜底方案的 trace 被标成警告，在 Langfuse 的 Traces 列表里按 Level 筛选，就能一次找出所有"规划失败"的请求，比翻日志快得多。
3. **反馈接口的安全问题**：任何人只要知道一个 trace_id，就能给它打分。现在没有登录系统，先接受这个风险；P11 讲权限时再回来补。

## 常见问题

| 现象 | 原因 |
|---|---|
| `docker: command not found` | Docker Desktop 装好后没打开过，或者还没启动完（看菜单栏鲸鱼图标） |
| `docker compose up` 拉镜像超时 / `TLS handshake timeout` | 网络问题，见 Step 0.1 的代理设置 |
| `port is already allocated` / `address already in use` | 端口被占用：`lsof -i :3000` 找到占用的程序关掉，或者改 compose 文件里冒号**左边**的端口 |
| http://localhost:3000 打不开或报 500 | 刚启动时数据库还在迁移，等一两分钟；`docker compose logs langfuse-web` 看报错 |
| 容器反复重启（`docker compose ps` 里显示 Restarting） | 内存不够，Docker Desktop → Settings → Resources 调大内存 |
| Langfuse 里一条 trace 都没有 | Key 填错（看启动日志有没有 `Langfuse 已启用`）；或者进程被强制杀掉，数据还没发出去 |

| 日志里的 request_id 全是 `-` | 中间件没生效，或者日志是在请求之外打印的（比如启动时） |
