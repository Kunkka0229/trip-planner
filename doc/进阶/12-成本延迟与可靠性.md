# P12：成本、延迟与可靠性

> **需求卡片**
> 上线一个月后的复盘会：
> 1. 月度模型账单超预算一倍。Langfuse 显示，记忆抽取、专家 Agent 这类"简单任务"占了 40% 的调用，用的却是最贵的模型。
> 2. 模型供应商上周有两次 502 故障，每次持续十几分钟，**这期间所有用户都生成失败**。
> 3. 节假日高峰，高德接口被限流，同一个城市的景点一天被查了几千次。
> 4. 有个用户写了个脚本，一小时生成了 300 次行程。
> 5. 地铁里网络一闪断，用户 40 秒的生成白等了，只能重来。
> 本迭代目标：**成本降 40%、单个供应商故障不影响可用性、断线可续传**，并且用 P2 的 trace 和 P3 的评测证明"省了钱，质量没有掉"。

**目标**：把系统从"能用"变成"扛得住"。学完你会掌握：模型路由（大小模型分工）、模型降级与重试（以及两个中间件之间的一个坑）、结果缓存（内存 / Redis）、Redis 原子计数和用户级限流、后台任务 + SSE 断线续传（`Last-Event-ID`）、LangGraph 的**持久执行**（进程挂了从检查点继续）、prompt 缓存的原理。

> 本课用真实的 uvicorn 服务验证过：**生成到一半断开连接，任务继续运行到结束，重连时带上 `Last-Event-ID`，补发了断线之后的事件**。开发中发现一个中间件组合的坑：`ModelRetryMiddleware` 默认会把最终的异常"吞掉"，导致外层的降级中间件永远不会切换（Step 4）。**没有用真实的模型和 Redis 测量成本、延迟的变化**，作业 1 让你自己测。

## 成本和延迟花在哪了

用 P2 的 Langfuse 看一次"生成 + 两轮修改"的 trace，大致是这样的分布（示意）：

| 环节 | 调用次数 | 适合的模型 | 优化手段 |
|---|---|---|---|
| 规划（generate） | 1~3 | 大模型 | 减少重试（P3 的 first_try 指标）、prompt 缓存 |
| 修改助手 | 每轮 2~4 | 大模型 | — |
| 专家 Agent（P10） | 每次委派 2+ | **小模型** | 模型路由 |
| 记忆抽取（P7） | 每轮 1 | **小模型** | 模型路由 |

**原则：先测量，再优化**。没有 P2 的 trace，你不知道钱花在哪；没有 P3 的评测，你不知道换了小模型之后质量有没有下降。这两课是本课的前提。

## Part 1：模型路由

### Step 1：三个模型 `app/services/llm_service.py`

把创建 `ChatOpenAI` 的代码抽成一个函数，`get_llm` 用它，再加两个：

```python
def build_chat_model(model: str, base_url: str, api_key: str) -> ChatOpenAI:
    """P12：主模型、小模型、备用模型都用这个函数创建，参数之外的配置保持一致"""
    settings = get_settings()
    return ChatOpenAI(
        model=model, api_key=api_key, base_url=base_url,
        timeout=settings.llm_timeout, max_retries=1, stream_usage=True,
    )


@lru_cache(maxsize=1)
def get_llm() -> ChatOpenAI:
    settings = get_settings()
    if not (settings.llm_api_key and settings.llm_base_url and settings.llm_model_id):
        raise LLMNotConfiguredError("LLM_API_KEY / LLM_BASE_URL / LLM_MODEL_ID 未配置完整")
    llm = build_chat_model(settings.llm_model_id, settings.llm_base_url, settings.llm_api_key)
    print(f"✅ LLM 初始化成功: model={llm.model_name}, base_url={settings.llm_base_url}")
    return llm


@lru_cache(maxsize=1)
def get_fast_llm() -> ChatOpenAI:
    """P12：小模型，做简单任务（记忆抽取、专家 Agent）。没配置时就用主模型"""
    settings = get_settings()
    if not settings.fast_llm_model_id:
        return get_llm()
    return build_chat_model(settings.fast_llm_model_id, settings.llm_base_url, settings.llm_api_key)


@lru_cache(maxsize=1)
def get_fallback_llm() -> ChatOpenAI | None:
    """P12：备用模型。最好是另一家供应商，这样主供应商整体故障时也能用"""
    settings = get_settings()
    if not settings.fallback_llm_model_id:
        return None
    return build_chat_model(
        settings.fallback_llm_model_id,
        settings.fallback_llm_base_url or settings.llm_base_url,
        settings.fallback_llm_api_key or settings.llm_api_key,
    )
```

### Step 4：Agent 的重试和降级 `app/guardrails/middleware.py`

```python
"""自定义中间件（P11）：话题限制、工具权限

LangChain 1.x 中间件的钩子（按执行顺序）：
  before_agent → [ before_model → wrap_model_call(调用模型) → after_model → wrap_tool_call(执行工具) ]×N → after_agent
前端类比：axios 的请求拦截器 / 响应拦截器，只是这里拦截的是"Agent 的每一步"
"""

from typing import Any, Awaitable, Callable

from langchain.agents.middleware import AgentMiddleware, ModelRequest, ModelResponse, ToolCallRequest, hook_config
from langchain_core.language_models import BaseChatModel
from langchain_core.messages import AIMessage, ToolMessage
from langgraph.types import Command

# 一看就和旅行无关的请求。真实项目里会用一个便宜的小模型做分类（P12 的模型路由），关键词只是第一道筛子
OFF_TOPIC_WORDS = ("写代码", "写程序", "写作业", "写论文", "写小说", "炒股", "股票", "翻译这段", "解方程")
OFF_TOPIC_REPLY = "我是旅行助手，只能帮你处理和这次旅行有关的事情，比如调整行程、查询景点信息、预订酒店。"


class TopicGuardMiddleware(AgentMiddleware):
    """跑题的请求直接回复固定的话，不调用模型

    为什么要做？公司的 Agent 按 token 付费。如果用户把它当成免费的通用聊天机器人（写代码、写作业），
    每一次都是公司在买单。另外，限制话题也能减少被诱导说出不当内容的风险
    """

    @hook_config(can_jump_to=["end"])  # 声明这个钩子可能会跳到 end，LangChain 会据此在图里加上对应的边
    async def abefore_agent(self, state: dict[str, Any], runtime) -> dict[str, Any] | None:
        text = state["messages"][-1].text
        if any(word in text for word in OFF_TOPIC_WORDS):
            return {"messages": [AIMessage(OFF_TOPIC_REPLY)], "jump_to": "end"}
        return None  # 返回 None：什么都不改，继续往下执行


# 工具 → 需要的权限。不在这里的工具，所有人都能用
TOOL_PERMISSIONS = {"book_hotel": "booking"}


class ToolPermissionMiddleware(AgentMiddleware):
    """按用户权限决定能用哪些工具（权限来自 runtime.context.permissions）

    两道关卡（纵深防御）：
      1. wrap_model_call：调用模型之前，把没有权限的工具从工具列表里拿掉，模型根本不知道有这个工具
      2. wrap_tool_call：真正执行工具之前再检查一次。万一模型"编造"了一个它看不到的工具调用，也执行不了
    """

    @staticmethod
    def allowed(name: str, permissions: frozenset[str]) -> bool:
        needed = TOOL_PERMISSIONS.get(name)
        return needed is None or needed in permissions

    async def awrap_model_call(
        self, request: ModelRequest, handler: Callable[[ModelRequest], Awaitable[ModelResponse]]
    ) -> ModelResponse:
        permissions = request.runtime.context.permissions
        tools = [t for t in request.tools if self.allowed(getattr(t, "name", ""), permissions)]
        # override：返回一个修改过的请求副本（不修改原对象），交给下一层（handler）继续处理
        return await handler(request.override(tools=tools))

    async def awrap_tool_call(
        self, request: ToolCallRequest, handler: Callable[[ToolCallRequest], Awaitable[ToolMessage | Command]]
    ) -> ToolMessage | Command:
        name = request.tool_call["name"]
        if not self.allowed(name, request.runtime.context.permissions):
            return ToolMessage(f"没有权限使用 {name}", tool_call_id=request.tool_call["id"], status="error")
        return await handler(request)


def guardrail_middlewares() -> list[AgentMiddleware]:
    """所有面向用户的 Agent 都要挂的护栏，放在中间件列表的最前面

    ModelCallLimitMiddleware(run_limit=12)：一轮对话最多调用 12 次模型。正常的修改用不了这么多，
      超过了说明模型陷入了循环（比如反复调用同一个失败的工具），及时止损（成本熔断）
    ToolCallLimitMiddleware(run_limit=20)：同理，限制工具调用总次数
    """
    from langchain.agents.middleware import ModelCallLimitMiddleware, ToolCallLimitMiddleware

    from app.guardrails.pii import pii_middlewares

    return [
        TopicGuardMiddleware(),
        *pii_middlewares(),
        ToolPermissionMiddleware(),
        ModelCallLimitMiddleware(run_limit=12, exit_behavior="end"),
        ToolCallLimitMiddleware(run_limit=20),
    ]


# 重试的初始等待时间（秒）。测试里会改小，不然每个失败用例都要等好几秒
RETRY_INITIAL_DELAY = 1.0


def reliability_middlewares(fallback: BaseChatModel | None) -> list[AgentMiddleware]:
    """P12：模型调用的重试和降级

    ModelFallbackMiddleware：主模型调用失败（重试之后仍然失败）时，换备用模型再试
    ModelRetryMiddleware：模型调用抛异常时，等一会儿重试（1 秒、2 秒……指数退避，带随机抖动）
    顺序：wrap_model_call 类的中间件，列表里靠前的在外层。降级在外、重试在内 =
      "主模型重试 2 次 → 还不行就换备用模型（备用模型同样有 2 次重试）"

    坑：ModelRetryMiddleware 默认 on_failure="continue"，重试用完后会把异常"吞掉"，变成一条
    "Model call failed after 3 attempts..." 的普通回复。外层的降级中间件看不到异常，就永远不会切换。
    所以有备用模型时必须用 on_failure="error"，把异常抛给外层
    """
    from langchain.agents.middleware import ModelFallbackMiddleware, ModelRetryMiddleware

    if fallback is not None:
        return [
            ModelFallbackMiddleware(fallback),
            ModelRetryMiddleware(max_retries=2, initial_delay=RETRY_INITIAL_DELAY, on_failure="error"),
        ]
    # 没有备用模型：重试用完后，给用户一句看得懂的话（默认的提示是英文，还带着异常细节）
    return [ModelRetryMiddleware(max_retries=2, initial_delay=RETRY_INITIAL_DELAY,
                                 on_failure=lambda exc: "抱歉，服务暂时繁忙，请稍后再试。")]
```

只看文件末尾新增的 `RETRY_INITIAL_DELAY` 和 `reliability_middlewares`。

**这是本课踩到的坑**：第一版我直接写了 `[ModelFallbackMiddleware(fallback), ModelRetryMiddleware(...)]`，测试里主模型连续失败，期望切换到备用模型，结果助手回复的是 `Model call failed after 3 attempts with ConnectionError: 502 Bad Gateway`。原因是 `ModelRetryMiddleware` 的 `on_failure` 默认是 `"continue"`：重试用完后，它不抛异常，而是**把错误变成一条普通的 AI 回复**。外层的降级中间件看到的是"调用成功了"，当然不会切换。

**教训**：中间件是一层套一层的，每一层"出错时做什么"会直接影响外层的行为。组合多个中间件时，一定要有测试覆盖"失败路径"。

`build_edit_agent` 增加 `fallback` 参数，中间件列表里护栏后面加上 `*reliability_middlewares(fallback)`；`build_supervisor` 同理。`assistant` 节点创建 Agent 时传入 `fallback=deps.fallback_llm`。

### 三层重试，别叠太多

现在系统里有三个地方会重试，要清楚它们各管什么：

| 层 | 管什么 | 次数 |
|---|---|---|
| `ChatOpenAI(max_retries=1)` | 单次 HTTP 请求的网络错误、429、5xx | 1 |
| `ModelRetryMiddleware` / generate 的重试循环 | 一次模型调用整体失败 | 2 |
| `ModelFallbackMiddleware` / `use_fallback` | 主模型重试后仍然失败，换供应商 | 1 |

最坏情况：(1+1) × (1+2) × 2 = 12 次请求，每次 `llm_timeout` 秒。**重试层数多了，故障时的等待时间会成倍增长**。如果供应商已经整体宕机，越早切换越好，宁可每层少重试一次。

## Part 3：缓存

### Step 5：缓存 `app/services/cache.py`

```python
"""缓存（P12）：同一套接口，两种实现
  MemoryCache：进程内存，单机开发用；进程重启就没了，多个进程之间不共享
  RedisCache： Redis，生产用；多个进程、多台机器共享同一份缓存

REDIS_URL 留空时用 MemoryCache，配置了（例如 redis://localhost:6379/0）就用 Redis
"""

import json
import time
from functools import lru_cache
from typing import Any, Protocol

from app.config import get_settings


class Cache(Protocol):
    async def aget(self, key: str) -> Any | None: ...
    async def aset(self, key: str, value: Any, ttl_seconds: int) -> None: ...
    async def aincr(self, key: str, ttl_seconds: int) -> int: ...


class MemoryCache:
    def __init__(self) -> None:
        self._data: dict[str, tuple[float, Any]] = {}  # key → (过期时间, 值)

    async def aget(self, key: str) -> Any | None:
        item = self._data.get(key)
        if item is None or item[0] < time.monotonic():
            self._data.pop(key, None)  # 过期了顺手删掉
            return None
        return item[1]

    async def aset(self, key: str, value: Any, ttl_seconds: int) -> None:
        self._data[key] = (time.monotonic() + ttl_seconds, value)

    async def aincr(self, key: str, ttl_seconds: int) -> int:
        """计数器 +1，返回新的值。第一次创建时设置过期时间（给限流用）"""
        count = (await self.aget(key) or 0) + 1
        expires = self._data[key][0] if key in self._data else time.monotonic() + ttl_seconds
        self._data[key] = (expires, count)
        return count


class RedisCache:
    def __init__(self, client) -> None:
        self.redis = client  # redis.asyncio.Redis

    async def aget(self, key: str) -> Any | None:
        raw = await self.redis.get(key)
        return json.loads(raw) if raw is not None else None

    async def aset(self, key: str, value: Any, ttl_seconds: int) -> None:
        # ex=过期秒数。Redis 会自动删除过期的 key，不用自己清理
        await self.redis.set(key, json.dumps(value, ensure_ascii=False), ex=ttl_seconds)

    async def aincr(self, key: str, ttl_seconds: int) -> int:
        # pipeline：把两条命令打包发送；transaction=True 时它们作为一个整体执行（MULTI/EXEC），中间不会插入别的命令
        # INCR 是原子操作：100 个请求同时 +1，结果一定是 100，不会出现"读到同一个旧值"的问题
        async with self.redis.pipeline(transaction=True) as pipe:
            pipe.incr(key)
            pipe.expire(key, ttl_seconds, nx=True)  # nx：只在 key 还没有过期时间时设置，不会每次都延长窗口
            count, _ = await pipe.execute()
        return count


@lru_cache
def get_cache() -> Cache:
    url = get_settings().redis_url
    if not url:
        return MemoryCache()
    import redis.asyncio as redis  # 只有配置了 Redis 才需要这个包

    return RedisCache(redis.from_url(url))
```

构造函数增加 `cache: Cache | None = None` 参数，并保存 `self.cache = cache`。`_aget` 拆成两层：

```python
    async def _aget(self, path: str, params: dict[str, Any], ttl: int = 0) -> dict[str, Any]:
        # P12：先查缓存。key 里只放请求参数，不放高德 Key（缓存的 key 可能出现在 Redis 的监控、日志里）
        cache_key = f"amap:{path}:{json.dumps(params, sort_keys=True, ensure_ascii=False)}"
        if self.cache is not None and ttl and (cached := await self.cache.aget(cache_key)) is not None:
            logger.debug("高德缓存命中: %s", cache_key)
            return cached
        data = await self._aget_uncached(path, params)
        if self.cache is not None and ttl:
            await self.cache.aset(cache_key, data, ttl)  # 只缓存成功的结果：失败会抛异常，走不到这里
        return data

    async def _aget_uncached(self, path: str, params: dict[str, Any]) -> dict[str, Any]:
        ...（原来 _aget 的内容）
```

`asearch_poi`、`aget_weather` 调用 `_aget` 时分别传 `ttl=POI_TTL`、`ttl=WEATHER_TTL`。`get_amap_client` 里传入 `cache=get_cache()`。

**要点**

1. **缓存的是高德的原始响应**，不是解析后的 `POIInfo`。解析逻辑以后改了（比如多解析一个字段），缓存里的数据照样能用。
2. **`json.dumps(params, sort_keys=True)`**：参数顺序不同但内容相同的请求，要得到同一个 key。
3. **为什么只给异步方法加缓存？** 规划图走的是异步方法，这是调用量最大的地方。同步方法只给 `/api/poi` 这些调试接口用。
4. **不要缓存失败的结果**，否则高德一次抖动，接下来一整天这个查询都是失败的。

### 关于 prompt 缓存

模型供应商（OpenAI、Anthropic、DeepSeek、百炼等）大多支持**前缀缓存**：如果这次请求的开头部分和最近某次请求一模一样，这部分 token 的价格会大幅降低（常见是正常价格的 10%~50%），速度也更快。不需要写代码，但要**让 prompt 的开头保持稳定**：

| 做法 | 本项目 |
|---|---|
| 固定不变的内容（规则、输出格式）放在最前面 | ✅ `PLANNER_SYSTEM_PROMPT` 是 system 消息，每次都一样 |
| 每次都变的内容（用户需求、候选数据、当前行程）放在后面 | ✅ PlannerContext 在 user 消息里；修改助手的 prompt 是"规则在前、行程在后" |
| 不要在开头放时间戳、随机 ID | ✅ |

在 Langfuse 里打开一次 generation，看 usage 里有没有 `cache_read` 之类的字段（不同供应商的叫法不一样），就知道缓存有没有命中。作业 2 让你实际观察。

## Part 4：限流

### Step 7：用户级限流 `app/services/rate_limit.py`

```python
"""用户级限流（P12）：每个用户每分钟最多发起多少次请求

为什么第 9 课已经有高德限速了还要这个？
  高德限速：保护"我们对高德"的调用不超过对方的额度
  用户限流：保护"我们自己"，一个用户（或者一个脚本）不能无限制地消耗模型额度

算法：固定窗口计数。key = 接口名 + 用户 + 当前是第几分钟，每来一个请求 +1，超过上限就拒绝
  简单可靠，缺点是窗口边界上可能瞬间放过 2 倍的请求（第 59 秒 5 次 + 第 61 秒 5 次）
  更平滑的做法是令牌桶 / 滑动窗口（作业 3）
"""

import time

from fastapi import HTTPException

from app.services.cache import get_cache


async def check_rate_limit(name: str, user_id: str, limit_per_minute: int) -> None:
    if limit_per_minute <= 0:
        return  # 0 = 不限流
    window = int(time.time() // 60)
    count = await get_cache().aincr(f"rl:{name}:{user_id}:{window}", ttl_seconds=60)
    if count > limit_per_minute:
        retry_after = 60 - int(time.time()) % 60
        # 429 Too Many Requests + Retry-After 响应头：告诉客户端多少秒后可以再试，这是 HTTP 的标准做法
        raise HTTPException(status_code=429, detail=f"请求太频繁，请 {retry_after} 秒后再试",
                            headers={"Retry-After": str(retry_after)})
```

`app/api/routes/trip.py` 导入 `from app.services.rate_limit import check_rate_limit`，在 `/plan`、`/plan/stream` 两个接口的开头加：

```python

```

`/chat` 接口在 `load_session` 之前加：

```python

```

**为什么限流要用 Redis？** 生产环境通常会部署多个后端进程（P13），每个进程各自在内存里计数的话，一个用户的请求被分到 4 个进程上，实际上限就变成了 4 倍。Redis 是所有进程共享的计数器，`INCR` 又是原子操作，几十个请求同时到达也不会数错（`test_redis_cache_and_atomic_counter` 验证了这一点）。

## Part 5：后台任务与断线续传

### Step 8：后台任务 `app/services/jobs.py`

```python
"""后台任务（P12）：生成行程和浏览器连接解耦

P4 的做法：SSE 连接断了就取消任务（省钱）
问题：手机切到后台、地铁里网络闪断、用户刷新页面……连接断了，40 秒的生成白做了，用户还得重来
本课的做法：
  1. 提交任务，立刻返回 job_id，任务在后台运行，不管有没有人在看
  2. 任务的每个事件都按顺序记下来（事件日志）
  3. 浏览器随时可以连上来"订阅"：先补发错过的事件，再实时推送新的事件
  4. 断线重连时带上 Last-Event-ID（SSE 标准），从断开的地方继续

局限：事件日志在进程内存里，只适合单进程。多进程 / 多机器部署时，事件日志要放到 Redis Streams 这类共享存储里，
或者使用 LangGraph Platform 自带的后台运行（background runs）功能
"""

import asyncio
import logging
import time
import uuid
from dataclasses import dataclass, field
from typing import Any, AsyncIterator, Awaitable, Callable

logger = logging.getLogger(__name__)

EmitFn = Callable[[dict[str, Any]], None]
JOB_TTL_SECONDS = 3600  # 任务结束一小时后清理


@dataclass
class Job:
    id: str
    user_id: str
    events: list[dict[str, Any]] = field(default_factory=list)
    done: bool = False
    finished_at: float = 0.0
    task: asyncio.Task | None = None
    # "有新事件了"的信号。每次通知后换一个新的 Event：正在等待的订阅者拿着旧的那个，会被唤醒；
    # 之后再来等待的订阅者拿到新的那个，等下一次通知（避免多个订阅者之间互相 clear 掉信号）
    changed: asyncio.Event = field(default_factory=asyncio.Event)

    def emit(self, event: dict[str, Any]) -> None:
        self.events.append(event)
        self._notify()

    def finish(self) -> None:
        self.done, self.finished_at = True, time.monotonic()
        self._notify()

    def _notify(self) -> None:
        self.changed.set()
        self.changed = asyncio.Event()

    async def follow(self, after: int = -1) -> AsyncIterator[tuple[int, dict[str, Any]]]:
        """订阅事件：先补发编号大于 after 的历史事件，再等新的事件，直到任务结束"""
        index = after + 1
        while True:
            while index < len(self.events):
                yield index, self.events[index]
                index += 1
            if self.done:
                return
            await self.changed.wait()


class JobManager:
    def __init__(self) -> None:
        self.jobs: dict[str, Job] = {}

    def start(self, user_id: str, work: Callable[[EmitFn], Awaitable[dict[str, Any]]]) -> Job:
        """work：和 P5 的 sse_response 一样的 job 函数（用 emit 发事件，返回最后的结果事件）"""
        self._cleanup()
        job = Job(id=uuid.uuid4().hex, user_id=user_id)

        async def run() -> None:
            try:
                job.emit(await work(job.emit))
            except Exception as exc:
                logger.exception("后台任务失败")
                job.emit({"type": "error", "message": str(exc)})
            finally:
                job.finish()

        job.task = asyncio.create_task(run())  # 引用保存在 job 里，job 保存在 self.jobs 里（P7 讲过的弱引用坑）
        self.jobs[job.id] = job
        return job

    def get(self, job_id: str, user_id: str) -> Job | None:
        job = self.jobs.get(job_id)
        return job if job is not None and job.user_id == user_id else None  # 只能看自己的任务（P5 的 IDOR）

    def _cleanup(self) -> None:
        now = time.monotonic()
        for job_id in [j.id for j in self.jobs.values() if j.done and now - j.finished_at > JOB_TTL_SECONDS]:
            del self.jobs[job_id]

    async def shutdown(self) -> None:
        """服务关闭：取消还在运行的任务。checkpointer 已经存下了它们的进度，见讲义"持久执行"一节"""
        for job in self.jobs.values():
            if job.task is not None and not job.task.done():
                job.task.cancel()
```

**和 P4 的对比**

| | P4：SSE 直连 | P12：后台任务 |
|---|---|---|
| 连接断开 | 取消任务（省钱） | 任务继续 |
| 重新连接 | 只能重新生成 | 补发错过的事件，接着看 |
| 适合 | 短任务、用户一直盯着 | 长任务、移动端、网络不稳定 |

两种方式各有道理，所以本课**保留了 P4 的接口**，新增了一组接口，前端可以按场景选择。

async def follow_plan_job(
    job_id: str,
    http: Request,
    user_id: UserId = "anonymous",
    # SSE 标准：浏览器的 EventSource 断线重连时，会自动带上最后收到的事件 id
    last_event_id: Annotated[int, Header(alias="Last-Event-ID")] = -1,
):
    job = http.app.state.jobs.get(job_id, user_id)
    if job is None:
        raise HTTPException(status_code=404, detail="任务不存在")

    async def stream() -> AsyncIterator[str]:
        events = job.follow(after=last_event_id).__aiter__()
        while True:
            try:
                index, event = await asyncio.wait_for(events.__anext__(), timeout=HEARTBEAT_SECONDS)
            except TimeoutError:
                yield ": ping\n\n"
                continue
            except StopAsyncIteration:
                break
            # "id: 序号" 是 SSE 的标准字段，浏览器会记住最后一个 id，重连时放进 Last-Event-ID 请求头
            yield f"id: {index}\n{sse(event)}"
        # 注意：这里没有 finally 里的 task.cancel()。连接断开不影响任务，这是和 P4 最大的区别

    return StreamingResponse(
        stream(), media_type="text/event-stream", headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"}
    )

## Part 6：持久执行（Durable Execution）

后台任务解决了"浏览器断线"，那"服务器重启"呢？发版、扩缩容、进程崩溃时，正在运行的任务会被中断。

**P5 引入的 checkpointer 早就把这个问题解决了一大半**：图每执行完一步，state 都存进了数据库。进程重启后，对同一个 thread 调用：

```python
await graph.ainvoke(None, {"configurable": {"thread_id": thread_id}}, context=deps)
```

输入传 `None` 的意思是"不是开始一次新的运行，而是**从上次停下的地方继续**"。已经完成的节点（比如调了 4 次高德的 collect）不会再执行，直接从 generate 开始。这就是 LangGraph 的**持久执行**，也是公司里选择 LangGraph 的重要原因之一。

可以这样模拟：generate 卡住时取消任务（相当于进程被杀），然后用 `ainvoke(None, ...)` 恢复，观察高德的请求次数没有增加。

**要在服务启动时自动恢复，还缺一块**：知道"哪些 thread 是运行到一半被中断的"。可以在任务开始时把 thread_id 记进一张表（或 Redis 集合），正常结束时删掉；启动时把表里剩下的逐个恢复。这是作业 4。
