# 第 7 课：让大模型的输出变可靠

**目标**：第 6 课的版本"偶尔能用"，这一课把它变成"**总能给用户一个合格的结果**"。

核心观念：**大模型的输出是不可信的外部输入**，和用户提交的表单一样，必须校验。我们建一道四层"安检门"，再加上重试和兜底：

```
大模型回复（一段文本）
  │
  ├─① 提取 JSON      "好的，这是行程 ```json {...} ``` 祝您愉快" → {...}
  ├─② 类型校验       TripPlan.model_validate（Pydantic，第 3 课）
  ├─③ 业务校验       天数对不对？日期对不对？三餐齐不齐？景点数量合不合理？
  ├─④ 预算重算       单价让模型填，总价由代码算
  │
  ├─ 任一步失败 → 带上"错在哪"重试（最多 3 次，temperature 逐次升高）
  └─ 3 次都失败 → 返回兜底方案（success=true，并在 message 里说明情况）
```

对应：参考仓库 `app/planner/output.py`（`extract_json_object`、`validate_trip_plan_shape`、`create_fallback_plan`）、`app/agents/trip_planner_agent.py`（`_generate_trip_plan_with_retries`）。

> 本课代码用"按顺序返回预设回复的假 LLM"测试了 4 种场景：输出夹带说明文字和代码块 → 第 1 次成功；天数不对 → 带着错误提示重试，第 2 次成功；先缺晚餐、再遇到网络超时 → 第 3 次成功；3 次都被截断 → 返回兜底方案。预算重算的结果也手工核对过。

## Step 1：安检门 `app/agents/output.py`

````python
"""大模型输出的"安检门"：提取 JSON → 结构校验 → 业务校验 → 预算重算

核心思想：大模型的输出是"不可信的外部输入"，和用户提交的表单一样，必须校验
"""

import json
import math
from datetime import timedelta
from typing import Any

from app.models.schemas import Budget, TripPlan, TripRequest

REQUIRED_MEALS = {"breakfast", "lunch", "dinner"}


class PlanValidationError(ValueError):
    """行程不符合业务规则。错误信息会反馈给大模型，所以要写得具体、可操作"""


def extract_json_object(text: str) -> dict[str, Any]:
    """从大模型的回复里抠出第一个完整的 JSON 对象

    能处理：
      - 前后有多余的文字："好的，这是您的行程：{...} 祝您旅途愉快"
      - Markdown 代码块：```json {...} ```
    """
    decoder = json.JSONDecoder()
    # 从每一个 "{" 的位置尝试解析，直到成功
    start = text.find("{")
    while start != -1:
        try:
            # raw_decode：从字符串开头解析出一个完整的 JSON 值，返回 (对象, 结束位置)
            # 和 json.loads 的区别是：后面跟着多余的文字也不会报错
            obj, _end = decoder.raw_decode(text[start:])
        except json.JSONDecodeError:
            start = text.find("{", start + 1)  # 这个位置解析不了，找下一个 "{"
            continue
        if isinstance(obj, dict) and "days" in obj:
            return obj
        # 解析出来的是某个内层小对象（比如 location），说明外层 JSON 不完整，继续往后找
        start = text.find("{", start + 1)
    raise PlanValidationError("输出中没有找到完整的行程 JSON 对象（可能被截断，或者不是 JSON）")


def trip_dates(request: TripRequest) -> list[str]:
    """行程中每一天的日期字符串（从 trip_planner.py 挪到这里，两个文件共用）"""
    return [(request.start_date + timedelta(days=i)).isoformat() for i in range(request.travel_days)]


def validate_plan(plan: TripPlan, request: TripRequest) -> None:
    """Pydantic 只能保证"类型对"，这里检查"业务对"。发现问题就抛 PlanValidationError"""
    dates = trip_dates(request)
    if len(plan.days) != len(dates):
        raise PlanValidationError(f"days 应该有 {len(dates)} 天，实际有 {len(plan.days)} 天")

    # zip 把两个列表按位置配对，相当于 JS 的 plan.days.map((day, i) => [day, dates[i]])
    # enumerate 同时拿到下标和值：for (const [i, x] of arr.entries())
    for i, (day, date) in enumerate(zip(plan.days, dates)):
        label = f"第 {i + 1} 天"
        if day.date != date:
            raise PlanValidationError(f"{label} 的 date 应为 {date}，实际为 {day.date}")
        if not 1 <= len(day.attractions) <= 3:  # Python 支持连续比较：1 <= x <= 3
            raise PlanValidationError(f"{label} 应安排 1-3 个景点，实际 {len(day.attractions)} 个")
        meal_types = {meal.type for meal in day.meals}  # 集合推导式，得到这一天出现过的餐别
        missing = REQUIRED_MEALS - meal_types  # 集合差集：应该有但是没有的
        if missing:
            raise PlanValidationError(f"{label} 缺少餐食: {', '.join(sorted(missing))}")


def recompute_budget(plan: TripPlan, request: TripRequest) -> Budget:
    """后端重新计算预算：大模型很不擅长算乘法和加法，单价可以让它填，总价必须由代码算

    计价口径：
      - 门票、餐饮：单价 × 人数
      - 酒店：单价（每间每晚）× 晚数 × 房间数；房间数按 2 人一间、向上取整
      - 交通：沿用大模型的估算（目前没有更可靠的数据来源）
    """
    people = request.party.total
    rooms = math.ceil(people / 2)  # 3 个人 → 2 间房
    llm_budget = plan.budget or Budget()
    return Budget(
        total_attractions=sum(a.ticket_price for d in plan.days for a in d.attractions) * people,
        total_meals=sum(m.estimated_cost for d in plan.days for m in d.meals) * people,
        total_hotels=sum(d.hotel.estimated_cost for d in plan.days if d.hotel) * rooms,
        total_transportation=llm_budget.total_transportation,
    )


def parse_and_check(text: str, request: TripRequest) -> TripPlan:
    """完整的安检流程：任何一步失败都会抛出 ValueError（或其子类）"""
    data = extract_json_object(text)
    plan = TripPlan.model_validate(data)  # 类型不对会抛出 ValidationError（也是 ValueError 的子类）

    # 能直接修正的就修正，不必为此重试一次：顶层的城市和日期以用户请求为准
    plan.city = request.city
    plan.start_date = request.start_date.isoformat()
    plan.end_date = request.end_date.isoformat()

    validate_plan(plan, request)
    plan.budget = recompute_budget(plan, request)
    return plan
````

### 为什么要后端重算预算？

计算过程：2 个成人加 1 个儿童，共 3 人；住 2 晚，按 2 人一间，需要 2 间房。

| 项目 | 大模型可能填的 | 代码计算 |
|---|---|---|
| 门票 | 忘了乘人数 | Σ单价 × 3 |
| 酒店 | 按人头算，或者忘了乘晚数 | Σ每晚单价 × 2 间 |
| 总价 | 加法算错，或者随手写个整数 | 由 `computed_field` 自动相加 |

**原则：凡是能用代码确定性算出来的东西，都不要交给大模型。** 参考仓库的 prompt 里花了大量篇幅教模型"怎么算预算"（第 8、9、10 条规则），最后还是在 rerank 阶段用代码重新计算了一遍，因为模型就是算不准。

## Step 2：规划 Agent 加重试和兜底 `app/agents/trip_planner.py`（整个文件替换）

> `trip_dates` 函数从这个文件挪到了 `output.py`，两个文件共用。

```python
"""旅行规划 Agent：查高德 → 调大模型 → 校验 → 失败重试 → 最终兜底"""

import json
from dataclasses import dataclass, field

from langchain_core.language_models import BaseChatModel
from langchain_core.messages import HumanMessage, SystemMessage

from app.agents.output import parse_and_check, recompute_budget, trip_dates
from app.agents.prompts import PLANNER_SYSTEM_PROMPT, build_planner_prompt
from app.models.schemas import POIInfo, TripPlan, TripRequest
from app.services.amap_client import AmapClient
from app.services.mock_planner import build_mock_plan

MAX_ATTEMPTS = 3  # 最多调用大模型几次
BASE_TEMPERATURE = 0.3


# @dataclass：自动生成 __init__ 等方法的轻量数据类，适合在函数之间传递结果
# 和 Pydantic 模型的区别：不做校验、不做序列化，只是一个"有名字的结构体"
@dataclass
class PlanResult:
    plan: TripPlan
    source: str  # "llm" = 大模型生成；"fallback" = 兜底方案
    attempts: int  # 一共调用了几次大模型
    errors: list[str] = field(default_factory=list)  # 每次失败的原因（用于日志和排查）


def compact_poi(poi: POIInfo) -> dict:
    """只保留大模型规划时需要的字段"""
    return {
        "name": poi.name,
        "address": poi.address,
        "district": poi.district,
        "location": poi.location.model_dump(),
        "rating": poi.rating,
        "cost": poi.cost,
    }


class TripPlanner:
    def __init__(self, amap: AmapClient, llm: BaseChatModel):
        self.amap = amap
        self.llm = llm

    def collect_candidates(self, request: TripRequest) -> dict[str, list[dict]]:
        """调高德收集候选（和第 6 课一样）"""
        keywords = request.preferences or ["景点"]
        attractions: list[POIInfo] = []
        for keyword in keywords[:3]:
            attractions += self.amap.search_poi(keyword, request.city, limit=8)
        hotels = self.amap.search_poi(request.accommodation, request.city, limit=8)
        foods = self.amap.search_poi("美食", request.city, limit=15)
        unique_attractions = list({poi.id: poi for poi in attractions}.values())
        return {
            "attractions": [compact_poi(p) for p in unique_attractions],
            "hotels": [compact_poi(p) for p in hotels],
            "foods": [compact_poi(p) for p in foods],
        }

    def plan(self, request: TripRequest) -> PlanResult:
        candidates = self.collect_candidates(request)
        weather = [w.model_dump() for w in self.amap.get_weather(request.city)]
        base_prompt = build_planner_prompt(
            request_json=request.model_dump_json(),
            candidates_json=json.dumps(candidates, ensure_ascii=False),
            weather_json=json.dumps(weather, ensure_ascii=False),
            dates=trip_dates(request),
        )

        errors: list[str] = []
        for attempt in range(1, MAX_ATTEMPTS + 1):  # 1, 2, 3
            prompt = base_prompt
            if errors:
                # 带错误提示重试：只把"上次错在哪"告诉模型，不把上次的整段输出塞回去
                # （整段输出很长，会让 prompt 越来越大，还可能让模型照着错误的格式继续写）
                prompt += f"\n\n注意：上一次的输出不合格，原因是：{errors[-1]}。请修正后重新输出完整 JSON。"

            # 每次重试稍微提高 temperature，让模型"换个思路"，避免反复犯同一个错误
            temperature = BASE_TEMPERATURE + 0.1 * (attempt - 1)
            messages = [SystemMessage(PLANNER_SYSTEM_PROMPT), HumanMessage(prompt)]

            try:
                response = self.llm.invoke(messages, temperature=temperature).text
                plan = parse_and_check(response, request)
            except Exception as exc:  # 网络错误、超时、解析失败、校验失败……都算这一次失败
                # 只保留第一行，Pydantic 的错误信息可能很长
                reason = f"{type(exc).__name__}: {str(exc).splitlines()[0]}"
                errors.append(reason)
                print(f"⚠️  第 {attempt}/{MAX_ATTEMPTS} 次失败: {reason}")
                continue

            print(f"✅ 第 {attempt} 次生成成功")
            return PlanResult(plan=plan, source="llm", attempts=attempt, errors=errors)

        # 所有重试都失败了：返回兜底方案，而不是直接报错。用户至少能看到一个能用的结果
        print("❌ 大模型多次生成失败，返回兜底方案")
        fallback = build_mock_plan(request)
        fallback.overall_suggestions = "智能规划暂时不可用，以下是基础行程模板，请稍后重试。"
        fallback.budget = recompute_budget(fallback, request)  # 兜底方案也按统一口径计算预算
        return PlanResult(plan=fallback, source="fallback", attempts=MAX_ATTEMPTS, errors=errors)
```

### 重试策略的取舍

| 策略 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 干净重试 | 原样再调用一次 | 简单；不会把错误格式"强化"给模型 | 模型可能犯同样的错 |
| **带错误提示重试（本课）** | prompt 末尾追加一句"上次错在哪" | 针对性强 | prompt 略微变长 |
| 修复式重试 | 把上次的完整输出和错误一起发回去，让模型修改 | 改动最小 | prompt 成倍膨胀；模型容易被错误的输出带偏 |

参考仓库选择的是**干净重试 + 提高 temperature**，源码注释里专门写了原因：它的 PlannerContext 很长，修复式重试会让上下文迅速膨胀。我们的折中做法是只追加一句错误原因，不回传整段输出。

### 两层重试：SDK 的重试和我们的重试

第 6 课创建 `ChatOpenAI` 时写了 `max_retries=1`，现在可以解释原因了。系统里其实有两层重试：

| | 由谁负责 | 重试什么 | 重试时 prompt 变不变 |
|---|---|---|---|
| 网络层 | `ChatOpenAI`（内部的 OpenAI SDK） | 429 限流、5xx、连接断开、超时 | 不变，原样重发 |
| 内容层 | 本课的 `for attempt in ...` 循环 | 格式错误、校验不通过，以及网络层重试之后仍然失败的请求 | 追加错误原因，提高 temperature |

两层是**相乘**的关系：一次调用最长等 `LLM_TIMEOUT=180` 秒，SDK 重试 1 次就是 2 次，再乘以我们的 3 次，最坏情况要等 180 × 2 × 3 = **18 分钟**，远远超过第 4 课前端设置的 5 分钟超时。SDK 默认重试 2 次，那就是 27 分钟。所以 SDK 的重试次数要调低，生产环境通常还会给整个生成过程再加一个总时长上限。

### LangChain 自带的结构化输出（了解）

LangChain 提供了一个现成的方法，可以直接把回复解析成 Pydantic 对象：

```python
# method="json_mode"：请求里带上 response_format={"type": "json_object"}，接口保证返回合法 JSON
structured_llm = self.llm.with_structured_output(TripPlan, method="json_mode")
plan = structured_llm.invoke(messages)  # 拿到的直接是 TripPlan 对象，不是文本
```

它能替代第 ① 步"提取 JSON"和第 ② 步"类型校验"，但**替代不了第 ③、④ 步**：天数对不对、三餐齐不齐、预算怎么算，这些是业务规则，只能自己写。另外要注意两点：

- `method` 默认是 `"json_schema"`，需要模型平台支持"按 JSON Schema 约束输出"，很多 OpenAI 兼容平台只支持 `json_mode`，以平台文档为准。
- 接口保证的只是"语法合法的 JSON"。输出太长被截断的话，照样会解析失败，所以重试和兜底仍然需要。

这也是本课手写安检门的原因：**框架能帮你省掉格式处理，但"什么样的行程算合格"只有你自己知道。**

> **兜底方案为什么返回 `success=true`？** 这是一个产品决策：用户拿到一份能用的基础行程，比看到一个红色报错更好。代价是前端必须把 `message` 显示出来，否则用户不知道这份行程是兜底生成的。参考仓库的做法相同（`generation_status == "fallback_success"`）。
