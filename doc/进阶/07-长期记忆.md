# P7：长期记忆

> **需求卡片**
> 老用户的抱怨："每次都要重新说一遍带一岁宝宝、不吃辣、不想太早起床，你们的 AI 记性也太差了。"
> 合规同学同时提醒：**用户必须能看到 AI 记住了自己什么，并且能删除**（《个人信息保护法》的查阅权、删除权）。
> 本迭代：**① 跨会话记住用户的稳定偏好，规划和修改时自动带上；② 新旧偏好冲突时能更新，而不是越记越乱；③ 用户可以查看、删除自己的记忆。**

**目标**：给 Agent 加上"长期记忆"。学完你会掌握：LangGraph Store 的 namespace 设计、在节点里通过 `runtime.store` 读写、用模型做"记忆抽取"并输出增删改操作、后台写入（以及 `asyncio.create_task` 的一个经典坑）、向量索引和语义召回、记忆的隐私与合规。

> 本课单独验证过 **SQLite 版 Store + 向量索引**能在你的 Mac 上运行（它依赖 sqlite-vec 扩展）。开发过程中踩到一个设计问题（后台记忆抽取和规划共用同一个模型对象，导致假模型的回复被"抢走"），已经在设计上解决，见 Step 3。**没有用真实的 embedding 模型验证语义召回效果**。

## 短期记忆 vs 长期记忆

| | 短期记忆（P5） | 长期记忆（本课） |
|---|---|---|
| LangGraph 组件 | checkpointer | **Store** |
| 按什么区分 | thread_id（一次会话） | namespace（任意层级，比如 `("users", 用户ID, "memories")`） |
| 存什么 | 这次会话的完整 state（对话、行程……） | 提炼过的、跨会话有用的信息 |
| 谁能读 | 只有同一个 thread | 任何会话、任何节点 |
| 类比 | 浏览器的 sessionStorage | 用户的账号资料 |

**为什么不直接把所有历史对话都塞给模型？** 一个老用户可能有几十个会话、上千条消息，全塞进去既贵又慢，还会被大量无关信息干扰。长期记忆是"提炼过的精华"：从对话里抽出"带一岁宝宝""不吃辣"这样的事实，几十个字就够了。

## 记忆系统的三个问题

| 问题 | 本课的做法 |
|---|---|
| **记什么**（什么值得记） | 用模型判断：只记稳定的偏好和事实，不记一次性的安排，不记敏感信息 |
| **怎么写**（新旧冲突） | 模型对比"已有记忆"和"新的话"，输出**增、改、删**三种操作，代码校验后执行 |
| **怎么读**（读哪些） | 用当前的需求做查询，召回最相关的几条；配置了 embedding 时按语义相似度排序 |

还有一个**什么时候写**：在回复用户之前写（热路径），还是回复之后在后台写？本课选后台，见 Step 3。

```python
"""长期记忆的存储：LangGraph Store

checkpointer（P5）vs store（P7）：
  checkpointer：按 thread 存，记的是"这一次会话"的完整状态，会话之间互不相通 → 短期记忆
  store：       按 namespace 存，任意会话都能读写，比如 ("users", "u1", "memories") → 长期记忆

STORE_URL 的写法和 CHECKPOINT_URL 一样：memory / sqlite:///... / postgresql://...
配置了 EMBEDDING_MODEL 时，会给记忆建向量索引，召回时按语义相似度排序；没配置时不排序，按存储顺序返回
"""

from contextlib import asynccontextmanager
from collections.abc import AsyncGenerator
from typing import Any

from langchain_openai import OpenAIEmbeddings
from langgraph.store.base import BaseStore
from langgraph.store.memory import InMemoryStore

from app.config import BACKEND_DIR, get_settings


def index_config() -> dict[str, Any] | None:
    """向量索引配置。fields=["text"]：只对记忆的 text 字段做 embedding"""
    settings = get_settings()
    if not settings.embedding_model:
        return None
    embeddings = OpenAIEmbeddings(
        model=settings.embedding_model,
        api_key=settings.llm_api_key,
        base_url=settings.llm_base_url,
        # OpenAI 兼容接口（百炼等）不支持 OpenAI 专用的"按 token 切分超长文本"逻辑，要关掉，否则会报错
        check_embedding_ctx_length=False,
    )
    return {"embed": embeddings, "dims": settings.embedding_dims, "fields": ["text"]}


@asynccontextmanager
async def open_store(url: str) -> AsyncGenerator[BaseStore, None]:
    index = index_config()
    if url == "memory":
        yield InMemoryStore(index=index)
    elif url.startswith("sqlite:///"):
        from langgraph.store.sqlite.aio import AsyncSqliteStore

        path = BACKEND_DIR / url.removeprefix("sqlite:///")
        path.parent.mkdir(parents=True, exist_ok=True)
        async with AsyncSqliteStore.from_conn_string(str(path), index=index) as store:
            await store.setup()  # 建表（向量索引用的是 sqlite-vec 扩展，安装 langgraph-checkpoint-sqlite 时已经带上了）
            yield store
    elif url.startswith(("postgresql://", "postgres://")):
        from langgraph.store.postgres.aio import AsyncPostgresStore  # 需要 pgvector 扩展才能用向量索引

        async with AsyncPostgresStore.from_conn_string(url, index=index) as store:
            await store.setup()
            yield store
    else:
        raise ValueError(f"不支持的 STORE_URL: {url}")
```

**namespace 是 Store 的核心设计**。它是一个元组，像文件路径一样分层：`("users", "u1", "memories")`。查询时传一个前缀，只会在这个"目录"下找。把 `user_id` 放进 namespace，**从存储结构上**保证了用户之间的隔离：查 u2 的记忆时，u1 的数据根本不在搜索范围里。比在每次查询时加 `WHERE user_id = ?` 更不容易出错。

## Step 3：召回与抽取 `app/memory/memories.py`

```python
"""用户的长期记忆：召回（读）和抽取（写）

一条记忆 = store 里的一个 item：
  namespace = ("users", 用户 ID, "memories")
  key       = 随机 ID
  value     = {"text": "带一岁宝宝出行，需要午休", "category": "party", "source": thread_id}
"""

import asyncio
import json
import logging
import uuid
from typing import Literal

from langchain_core.language_models import BaseChatModel
from langchain_core.messages import HumanMessage, SystemMessage
from langgraph.store.base import BaseStore, SearchItem
from pydantic import BaseModel, Field

logger = logging.getLogger(__name__)

MAX_MEMORIES = 30  # 每个用户最多记多少条，太多了召回时噪音大，也占 prompt


def namespace(user_id: str) -> tuple[str, ...]:
    return ("users", user_id, "memories")


# ---------- 读：召回 ----------

async def recall(store: BaseStore | None, user_id: str | None, query: str, limit: int = 8) -> list[str]:
    """召回和 query 最相关的记忆。有向量索引时按语义相似度排序，没有时 query 不起作用，按存储顺序返回前 limit 条"""
    if store is None or not user_id:
        return []
    items = await store.asearch(namespace(user_id), query=query, limit=limit)
    return [item.value["text"] for item in items]


def format_memories(memories: list[str]) -> str:
    """拼进 prompt 的文字。说清楚优先级：本次需求 > 长期偏好"""
    if not memories:
        return ""
    lines = "\n".join(f"- {m}" for m in memories)
    return f"\n\n【用户的长期偏好】（来自以往的对话；和本次需求冲突时，以本次需求为准）\n{lines}"


# ---------- 写：抽取 ----------

EXTRACT_SYSTEM_PROMPT = """你负责维护旅行助手对用户的长期记忆。你会看到"已有的记忆"和"用户刚说的话"，
判断有没有值得长期记住的信息，输出要做的修改。

值得记住的：会在以后的旅行中反复用到的稳定偏好和事实。
  例如：同行人员情况（带一岁宝宝、父母年纪大）、饮食（不吃辣、素食）、节奏（不喜欢早起）、住宿（只住连锁酒店）、兴趣（喜欢小众博物馆）
不要记住的：
  - 只和这一次旅行有关的安排（"这次想去故宫"、"第二天换个餐厅"）
  - 敏感信息：身份证号、手机号、详细住址、银行卡、具体的病情

规则：
- 新信息和已有记忆说的是同一件事、但内容变了 → update（例如以前"不吃辣"，现在说"可以吃一点辣了"）
- 用户明确否定了某条记忆 → delete
- 每条记忆一句话，以用户为主语，例如"带一岁宝宝出行，中午需要回酒店午休"
- 没有要改的就输出空列表

只输出一个 JSON 对象：
{"add": [{"text": "...", "category": "party|diet|pace|lodging|interest|budget|other"}],
 "update": [{"key": "已有记忆的 key", "text": "新的内容"}],
 "delete": ["已有记忆的 key"]}"""


class NewMemory(BaseModel):
    text: str = Field(min_length=2, max_length=100)
    category: Literal["party", "diet", "pace", "lodging", "interest", "budget", "other"] = "other"


class UpdatedMemory(BaseModel):
    key: str
    text: str = Field(min_length=2, max_length=100)


class MemoryOps(BaseModel):
    add: list[NewMemory] = []
    update: list[UpdatedMemory] = []
    delete: list[str] = []


async def list_memories(store: BaseStore, user_id: str) -> list[SearchItem]:
    # 不带 query 的 search：返回这个 namespace 下的 item（最多 MAX_MEMORIES 条）
    return await store.asearch(namespace(user_id), limit=MAX_MEMORIES)


async def update_memories(store: BaseStore, llm: BaseChatModel, user_id: str, user_texts: list[str], source: str) -> MemoryOps:
    """让模型对比"已有记忆"和"新的话"，输出增删改操作，再由代码执行

    为什么不直接把新的话存下来？
      - 大部分话不值得记（"第二天换个餐厅"）
      - 新旧信息会冲突，只追加不更新，记忆里就会同时有"不吃辣"和"爱吃辣"
    """
    texts = [t.strip() for t in user_texts if t and t.strip()]
    if not texts:
        return MemoryOps()
    existing = await list_memories(store, user_id)
    existing_view = [{"key": item.key, "text": item.value["text"]} for item in existing]
    prompt = (
        f"【已有的记忆】\n{json.dumps(existing_view, ensure_ascii=False)}\n\n"
        f"【用户刚说的话】\n" + "\n".join(f"- {t}" for t in texts)
    )
    response = await llm.ainvoke([SystemMessage(EXTRACT_SYSTEM_PROMPT), HumanMessage(prompt)], temperature=0)
    text = response.text
    ops = MemoryOps.model_validate_json(text[text.find("{") : text.rfind("}") + 1])

    # 模型给出的 key 必须真实存在：不能让它凭空"更新"或"删除"一条不存在的记忆
    known = {item.key: item for item in existing}
    ns = namespace(user_id)
    for item in ops.update:
        if item.key in known:
            category = known[item.key].value.get("category", "other")  # 更新内容，保留原来的分类
            await store.aput(ns, item.key, {"text": item.text, "category": category, "source": source})
    for key in ops.delete:
        if key in known:
            await store.adelete(ns, key)
    room = MAX_MEMORIES - len(known) + len([k for k in ops.delete if k in known])
    for memory in ops.add[: max(room, 0)]:
        await store.aput(ns, uuid.uuid4().hex, {"text": memory.text, "category": memory.category, "source": source})
    logger.info("记忆更新: +%d ~%d -%d", len(ops.add), len(ops.update), len(ops.delete))
    return ops


class MemoryWriter:
    """在后台更新记忆，不拖慢用户的请求

    热路径 vs 后台：
      热路径：回复用户之前先更新记忆 → 每次对话多等一次模型调用
      后台：  先回复用户，再慢慢整理记忆 → 用户无感；代价是"刚说的话"要到下一轮才生效
    记忆不需要实时生效，所以选后台
    """

    def __init__(self, llm: BaseChatModel | None) -> None:
        # 记忆抽取用自己的模型，不和规划共用：
        #   1. 可以换成更便宜的小模型（抽取偏好是个简单任务，P12 讲模型路由）
        #   2. 后台任务不会和主流程抢同一个模型对象（测试里的假模型就是被抢了才发现这个问题）
        # llm 为 None（没配置大模型）时，什么都不做
        self.llm = llm
        # 必须保存任务的引用！asyncio 只对任务保持"弱引用"，没人引用的任务可能在执行到一半时被垃圾回收
        # （Python 官方文档 asyncio.create_task 的 Important 提示里专门讲了这个坑）
        self._tasks: set[asyncio.Task] = set()

    def schedule(self, store: BaseStore | None, user_id: str, texts: list[str], source: str) -> None:
        if store is None or self.llm is None:
            return
        llm = self.llm

        async def run() -> None:
            try:
                await update_memories(store, llm, user_id, texts, source)
            except Exception:  # 记忆是锦上添花的功能，失败了记日志就行，不能影响主流程
                logger.exception("更新记忆失败")

        task = asyncio.create_task(run())
        self._tasks.add(task)
        task.add_done_callback(self._tasks.discard)  # 任务结束后自动从集合里移除

    async def drain(self) -> None:
        """等所有后台任务完成：服务关闭前调用，测试里也用它"""
        if self._tasks:
            await asyncio.gather(*self._tasks, return_exceptions=True)
```

**要点**

1. **抽取的输出是"操作"，不是"记忆"**。如果只让模型输出"新的记忆列表"，就只能追加，旧的"不吃辣"和新的"能吃微辣"会同时存在，召回时互相矛盾。让模型看着已有记忆（带 key）输出 `add / update / delete`，冲突就能被解决。
2. **代码要校验模型给的 key**。模型可能编造一个不存在的 key 去 update 或 delete。`if item.key in known` 这一行就是在防这个：**模型的输出永远是不可信输入**（第 7 课的原则在这里又出现了）。
3. **记什么、不记什么写在 prompt 里**，特别是"不要记敏感信息"。用户随口说了身份证号，绝不能变成一条永久记忆。P11 还会在更底层加一道 PII 过滤。
4. **`MemoryWriter` 用自己的模型**。第一版我让后台抽取直接用规划的 `deps.llm`，结果测试大面积失败：后台任务和主流程在同一个事件循环里并发运行，把假模型预设给主流程的回复"抢"走了。这暴露的是真实的设计问题：记忆抽取是个简单任务，本来就应该用**更便宜的小模型**（P12 会正式讲模型路由），和规划模型分开配置。
5. **`asyncio.create_task` 的坑**：Python 官方文档专门提醒过，事件循环对任务只保持**弱引用**，如果你创建任务后不保存它的引用，它可能在执行到一半时被垃圾回收，**没有任何报错，记忆就是没写进去**。所以 `MemoryWriter` 用一个 `set` 保存所有正在运行的任务，完成后再自动移除。
6. **后台写入的代价**：用户这一轮刚说"不吃辣"，如果马上又生成一个新行程，记忆可能还没写完。对"偏好"这种信息，晚一轮生效完全可以接受。如果是"用户刚说了预算改成 5000"，就不该走长期记忆，而应该直接进当前会话的 state。

## Step 7：我的记忆 `app/api/routes/me.py`

```python
"""P7：用户查看和删除自己的长期记忆

《个人信息保护法》要求用户能查阅、删除自己的个人信息。"AI 记住了我什么"必须对用户透明、可控
"""

from typing import Annotated

from fastapi import APIRouter, Header, HTTPException, Request
from pydantic import BaseModel

from app.memory.memories import list_memories, namespace

router = APIRouter(prefix="/me", tags=["我的"])

UserId = Annotated[str, Header(alias="X-User-Id", max_length=64)]


class MemoryItem(BaseModel):
    key: str
    text: str
    category: str
    updated_at: str


@router.get("/memories", response_model=list[MemoryItem], summary="我的长期记忆")
async def get_memories(http: Request, user_id: UserId = "anonymous"):
    items = await list_memories(http.app.state.store, user_id)
    return [
        MemoryItem(key=i.key, text=i.value["text"], category=i.value.get("category", "other"),
                   updated_at=i.updated_at.isoformat())
        for i in items
    ]


@router.delete("/memories/{key}", summary="删除一条记忆")
async def delete_memory(key: str, http: Request, user_id: UserId = "anonymous"):
    store = http.app.state.store
    # namespace 里带着 user_id：只能删自己的，别人的 key 在自己的 namespace 里根本找不到
    if await store.aget(namespace(user_id), key) is None:
        raise HTTPException(status_code=404, detail="记忆不存在")
    await store.adelete(namespace(user_id), key)
    return {"success": True}


@router.delete("/memories", summary="清空我的全部记忆")
async def clear_memories(http: Request, user_id: UserId = "anonymous"):
    store = http.app.state.store
    items = await list_memories(store, user_id)
    for item in items:
        await store.adelete(namespace(user_id), item.key)
    return {"success": True, "deleted": len(items)}
```

## 记忆系统在公司里还要考虑的

| 问题 | 说明 |
|---|---|
| 记忆过期 | "孩子一岁"一年后就不对了。可以给记忆加 `ttl`（Store 的 `aput` 支持），或者记录时间让模型判断 |
| 记忆污染 | 用户开玩笑说"我是素食者"，之后所有行程都没肉了。重要的记忆可以先问一句"要记住吗？" |
| 多人共用账号 | 一家人共用一个账号，偏好会混在一起。namespace 可以再细分到"出行人" |
| 评测 | 召回对不对、抽取对不对，都需要评测集（作业 3） |
| 合规 | 记忆是个人信息：要告知用户、能查看、能删除；注销账号时要彻底删除 |
